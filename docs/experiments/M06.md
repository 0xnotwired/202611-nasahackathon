## Interpretation decisions (not contract changes)

The contract text leaves these open. Each is a reviewable choice, made toward less certainty; the orchestrator may overrule any of them.

- **D-M06-1 Return shape.** Success returns the plain object of CONTRACTS.md §4 (`.points`, `.total`, `.record`), as the existing contract suite already assumes. A foreseen failure returns `{ ok: false, error: { code, field, message } }`. A caller checks `result.ok === false` first.
- **D-M06-2 Primary group.** `series.points` holds the comparable group with the most points; ties go to the group with the more recent latest point, then to a stable key order. Every other group is in `non_comparable_groups` with the reason from `core.areComparable`. Comparability is decided only by `core.areComparable`, not reimplemented.
- **D-M06-3 Days.** Gaps are UTC calendar days in `[from, to)`. A day is a gap when it has no point in the primary group; its reason says why (`no_record`, `not_recorded`, `confirmed_none`, `no_value`, `other_group`).
- **D-M06-4 `attention` precedence.** Absence in the record (`not_recorded`, `confirmed_none`, no numeric value, unknown unit) is reported before a missing criterion, so a `not_recorded` record never reads as merely "no criterion". Boundaries are inclusive: `low <= value <= high` is `within`.
- **D-M06-5 Additive fields.** `baseline.excluded_non_comparable` and `environment.coverage.segments` are not in CONTRACTS.md. Without them a baseline would hide records of another method and a coverage window would show a hole as continuous. They are additive; a request to adopt them is in the report, not applied to the contract.
- **D-M06-6 Technical bound.** A series range over 3650 days is refused. This is a size bound, not a medical range.

## Refuted and surprises

- **No prediction from the work order was refuted.**
- **Surprise 1: the first X6 run failed.** Rival explanations: (a) a bug in `environment`; (b) a bad fixture. The cheapest test that tells them apart was the failure message: it came from `saveBatch` in my helper (`invalid_field: value`), before `environment` ran. The store rejected an environment record I built without `value`. Explanation (b) held; the fixture got a default value and the test then passed unchanged in intent.
- **Surprise 2: a negative-control pattern for X1 did not match** (script error: an extra parenthesis). The script refuses to run on a pattern that does not occur exactly once, so no silent no-op happened. Fixed and rerun: red on X1.
- **Surprise 3 (my probe, not the module): saving 2000 CGM records in one `saveBatch` fails** with `invalid_field: object`, so my first real-data probe saved nothing and its glucose lines (`points: []`) were meaningless. Rival explanations: the importer output is invalid, or a size bound of the store. I did not diagnose the exact bound; the same records save in batches of 256 (as `scripts/import-real-samples.py` does), so the probe was repeated that way and the result in "Runs" is from that second probe. The first probe's glucose lines are discarded.
- **Finding for the orchestrator (not a defect of M06): real imported data is unreachable through M06.** CRF and BUT CGM records carry `time: null` with a `source_time`, so `series`, `latest`, `baseline` and `cumulative` correctly refuse with `unresolved_time` (CONTRACTS.md: avoid UTC age and placement). Any view over real data (M22, parts of M08/M09/M11) needs a query path that orders by source time within one clock scope, calendar and precision. That is a contract decision; nothing was added.
- **Foundation tests turn red when M06 lands, as the contract README says.** `readings: suite rejects its placeholder` and `G0-W1` fail because `tests/contract/registry.js` still lists `readings` as a placeholder. Hypothesis: that is the only cause. Test: temporarily adding `'readings'` to `implementedNames` gave 122/122, then the file was reverted with `git checkout` (`git status tests/` empty). The orchestrator makes that one-word change.

## Not verified

- **Not reviewed by anyone else.** Every line above is RUN by the builder; the independent replication, with two breakages of the reviewer's own, has not happened. Per AGENTS.md this record is not an approval and `modules.csv` is not touched.
- **IndexedDB backend.** All tests use the memory store. The real-shape probe also used memory. Queries against the real IndexedDB profile were not run.
- **Order of magnitude and speed.** `loadActive` reads every record of a subject and variable. Only 3016 records were exercised, and only for the `unresolved_time` path; no timing was measured.
- **Calendar-day gaps use UTC days.** A person's local day or a mission day is not modelled; a record near midnight UTC lands on the UTC day.
- **Duplicate timestamps.** Two records at the same instant are ordered by id; no test covers which one a view should prefer, and the rule is arbitrary.
- **A correction in a different variable** is not applied (the query reads one variable).
- **R6 by reading.** The tripwire cannot see a threshold hidden in a string, a lookup table or an expression built from allowed numbers. A reviewer reads `attention.js` and `analysis.js` for comparisons against measured values that do not come from `attention_criteria` (READ).
- **Additive fields** `baseline.excluded_non_comparable` and `environment.coverage.segments` were not in CONTRACTS.md when this record was written. They were adopted afterwards in contract 0.9, on the user's explicit authorization, together with the failure shape, `unresolved_time` and `not_comparable`. That adoption is a documentation change; no module code changed, and no reviewer has yet checked it.
- **Clinical validity.** Nothing here is clinical; no threshold, normal range or equivalence exists in the module.
