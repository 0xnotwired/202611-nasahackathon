## F1 — Data core (level 0)

**Claim.** A record that enters the store comes out with the same id, state, origin and subject, and a malformed record cannot enter at all.

**Modules.** Wave 1: M01, M02, M03. Wave 2: M04, M05. **Rules that start here:** R1, R3, R4, R7, R9.

| Id | Experiment | Prediction | Negative control |
|---|---|---|---|
| G1-W1 | Generate the scenario with seed 1, save it, list it | Every record comes back deep-equal; the count per state and per origin is the same before and after | Make the store turn `not_recorded` into `confirmed_none`: red |
| G1-W2 | Try to change and to delete a saved record through every store function | No function does it; the record is unchanged | Allow `updateState` on `records`: red |
| G1-W3 | Save a record with a missing field through every door that accepts records | None accepts it | Remove validation from `saveBatch`: red |
| G1-W4 | In a browser: save, close, reopen | The same records (BROWSER) | Fresh profile: empty |

**The claim is false if** any path lets a record in without validation, or any output differs from what was saved.

## Pre-gate adversarial review

READ: Each module has a separate builder and independent replication record.

reran the module and contract suites, and reviewed the layer before the
integrated positive gate. No clinical rules, real dataset import, network
sharing or hidden fallback were introduced. Only the declared store methods

RUN: Independent review found and corrected test-oracle gaps for valid zero
and negative measurements, empty equipment and negative criterion bounds,
conservative source-reading levels, duplicate ids inside a fresh batch, and
task procedure/subject/result references. The actual implementations were
already correct in those cases; repeat mutation checks now detect them.

READ: The browser gate design was independently reviewed before execution.
Its fresh-profile control now requires a successful empty list plus a named
not_found result; private-context tests actually save/read/reopen. Failure
controls have operation-specific reasons, and the store API surface excludes
undeclared deletion doors. Raw future-version state injection is explicitly
coupled to the current IndexedDB adapter layout, not a public product API.
