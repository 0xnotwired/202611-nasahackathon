## Refuted and surprises

READ: The first immutability probe attempted a state change that core would independently reject while retaining a numeric value. That could mask a missing history guard. The oracle was strengthened before mutation execution to attempt a valid numeric value update. RUN: The actual source mutation permitting records/shared updates was then detected on that valid-value assertion; the actual implementation rejects the update. No unexecuted initial mutation is counted as runtime evidence.

READ: Implementation uses readwrite IndexedDB transactions covering the complete collection snapshot, validation, duplicate/provenance decisions and writes. No asynchronous work outside IndexedDB request callbacks is awaited inside the transaction. Both adapters enforce a technical capacity of 10,000 collection objects, batches at most 2,048 entries, and bounded plain JSON snapshots; these are resource limits, not medical limits. Collection-specific non-record business rules remain the owning modules' responsibility.

## Not verified

READ: No encryption, sync, backup, production UI, clinical validation or multi-device behavior. IndexedDB persistent means this backend can retain data across normal browser restart; browser eviction, OS compromise, corruption and privacy-mode retention across browser shutdown are not guaranteed. The private check verified an incognito context's actual availability/status, not indefinite retention. Only installed Chromium was tested.

READ: IndexedDB unknown-version read refusal was verified by deliberately corrupting the raw database outside the product API. The store fails closed for the affected collection, including when a corrupt row differs from the requested id. Technical validation rejects ordinary accessors without invoking them; live Proxy trap code cannot be sandboxed by a JavaScript API and is not claimed safe.
