## Decision details

| Decision | Alternative rejected | Reversibility | Revisit when |
|---|---|---|---|
| `start` receives the procedure object and copies its version into the execution | A registry that is read on every call (the version would move with it, R5) | Two-way | A procedure registry exists |
| A blocked execution is stored, with `missing`; no transition leaves `blocked` | Returning blocked without storing (the attempt would leave no trace) | Two-way | The plan needs to start over from a blocked one |
| An optional `clock` in the transition options; without it `updated` is unchanged | `Date.now()` (invents a time and breaks tests) or a required clock (the contract test calls without one) | Two-way | The contract adds a clock to every transition |
| One lock chain per execution id inside the module | A store with compare-and-set (it has none) | Two-way | The store offers an atomic update |

## Negative controls

Scratchpad `mutate-f3.mjs`: 15 controls, each turns its named test red: blocked start proceeds (P1), alternative always attached (P2), resume resets the step and interrupt completes (P3), version read from elsewhere (P4), resume allowed from in_progress and completed finished again (P5), difficulties dropped (P6), no lock (X2), completed with steps left and step past the last (X3), foreign and unknown record linked (X4), time invented (X5), duplicate step ids (X1). P4's control changes the version to another value, because the design copies the version at start and has no registry to read from.

## Refuted and surprises

No prediction refuted. Design note: the work order's P4 control ("read the current procedure") has no direct counterpart because `advance` receives no procedure; the version is fixed at `start`.

## Not verified

No procedure registry or publishing step exists, so "publish version 2" is simulated by passing another object. The lock is per process: two browser tabs on one IndexedDB can still interleave. No clinical content: the only procedure is the team's fictional demo.
